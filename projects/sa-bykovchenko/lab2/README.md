# Лабораторная работа № 2. Построение RAG-агента по документации

Выполнила Быковченко Софья. P4255

## Цель работы

В этой работе я реализовала систему ответов на вопросы по техническому документу. Сначала система находит подходящие фрагменты, затем передаёт их языковой модели, которая составляет ответ и указывает источники. Такой подход называется RAG (Retrieval-Augmented Generation).

Основные задачи эксперимента:

- подготовить текст PDF и сохранить связь фрагментов с исходными страницами;
- сравнить способы разбиения текста и режимы поиска;
- проверить, насколько правильно модели используют найденную информацию;
- реализовать сервис, в котором можно задать вопрос и получить ответ с источниками.

В итоговой версии для поиска выбрана конфигурация **markdown_header 256/32, hybrid**. Поиск оценён на текущем корпусе с парсером 3.2.0. Сравнение ответов Gemma и Qwen выполнено отдельным прогоном на предыдущей сборке корпуса; эти результаты приведены отдельно и не приписываются новой конфигурации.

## Данные и подготовка текста

Для работы выбран технический отчёт NASA *Apollo 11 Mission Report* (MSC-00171, 1969). В нём описаны полёт, действия экипажа, научные эксперименты и неисправности оборудования. Исходный PDF содержит **359 страниц**.

PDF преобразуется в Markdown с помощью **PyMuPDF4LLM**. Используется существующий текстовый OCR-слой документа. 
Код обработки находится в `source/parsing.py`, запуск в `source/parse_documents.py`, настройки в `config/parser.json`.

В поиск включаются страницы, содержащие не менее 200 символов текста и не более 5% не-ASCII букв. 
Для каждой страницы сохраняется признак включения в поиск и причина исключения.

| Показатель | Итоговое значение |
|---|---:|
| Страниц в исходном PDF | 359 |
| Страниц, включённых в поиск | 250 |
| Текстонасыщенных страниц, не менее 300 символов | 233 |
| Страниц с таблицами, обнаруженными библиотекой | 65 |
| Заголовков разделов, добавленных в Markdown | 206 |

Заголовки глав задаются конфигурацией документа, заголовки разделов дополнительно выделяются при обработке текста. 
Такой проход нужен из-за особенностей скана: определение структуры только по размерам шрифта здесь недостаточно. 
Для каждой страницы сохраняются номер в PDF, печатный номер, глава, источник и ссылка на PDF с `#page=N`. 
Номер страницы PDF и напечатанный номер страницы могут различаться.

## Как устроен пайплайн

Подготовка корпуса выполняется заранее. При поступлении вопроса используются уже сохранённые чанки и индексы.

| Этап | Что выполняется | Основной код |
|---|---|---|
| Подготовка документа | PDF преобразуется в постраничный Markdown с метаданными | `parsing.py`, `parse_documents.py` |
| Разбиение | Текст делится на чанки с учётом заголовков и токенового бюджета | `chunking.py` |
| Представления | Для чанков вычисляются E5-векторы и строится BM25 | `embeddings.py`, `sparse.py`, `build_index.py` |
| Хранилище | Векторы записываются в FAISS HNSW и FlatIP вместе с привязкой к текстам | `vector_store.py`, `load_to_vector_store.py` |
| Поиск | Вопрос кодируется E5; выполняется dense, sparse или hybrid-поиск | `source_loader.py`, `retriever.py` |
| Контекст | Найденные фрагменты дедуплицируются, получают номера ссылок и помещаются в бюджет | `context_builder.py` |
| Ответ | Контекст и вопрос передаются в Ollama; ответ разбирается и проверяется | `generation.py`, `rag_answer.py` |
| Сервис | Тот же RAG-пайплайн доступен через HTTP и браузерный чат | `serve_rag.py` |

Парсинг, базовое разбиение текста, получение эмбеддингов, BM25, FAISS и стандартные IR-метрики используют готовые библиотеки. Собственный код связывает эти этапы, сохраняет метаданные, проверяет артефакты и организует эксперименты.

## Построение индекса

### Разбиение на чанки

В основном варианте используются `MarkdownHeaderTextSplitter` и `RecursiveCharacterTextSplitter` из **langchain-text-splitters**. Сначала выделяются части страницы по заголовкам, затем слишком длинные части делятся на фрагменты с ограничением по токенам и перекрытием.

Иерархия заголовков переносится на продолжение раздела на следующей странице. При этом **каждый чанк остаётся в пределах одной страницы**. Тексты разных разделов не склеиваются в один чанк. Это позволяет указывать точную страницу источника, хотя граница страницы может разрывать предложение.

Для сравнения используется `page_recursive`: страница делится рекурсивно без предварительного структурного разбиения по заголовкам разделов.

| Способ разбиения | Размер чанка, токенов | Перекрытие, токенов | Количество чанков | Сохранённые evidence-цитаты |
|---|---:|---:|---:|---:|
| markdown_header | 256 | 32 | 832 | 56/56 |
| markdown_header | 384 | 64 | 634 | 56/56 |
| markdown_header | 480 | 80 | 555 | 56/56 |
| page_recursive | 384 | 64 | 532 | 55/56 |

Размер ограничивает весь текст, поступающий в embedding-модель: префикс `passage:`, путь заголовков, тело чанка и специальные токены. Длина измеряется токенизатором E5 и проверяется после разбиения. Перекрытие задаётся для соседних фрагментов внутри разделяемого текста; оно не переносит текст через границу страницы или раздела. Короткие разделы и последние фрагменты могут быть меньше заданного размера.

Вариант `page_recursive` потерял одну полную evidence-цитату для Q04 на странице PDF 40: она оказалась разрезана границей чанков.
### Эмбеддинги и режимы поиска

Векторные представления получены с помощью **`intfloat/multilingual-e5-small`** через SentenceTransformer. 
Модель многоязычная, поэтому вопрос на русском можно сопоставить с английским текстом отчёта. 
Для вопросов используется префикс `query:`, для документов `passage:`.

Представления токенов усредняются с учётом маски внимания и L2-нормализуются. Размерность вектора **384**. 
Для нормализованных векторов скалярное произведение соответствует косинусному сходству.

Поддерживаются три режима:

- **dense** поиск по сходству E5-векторов
- **sparse** лексический поиск BM25 через библиотеку `rank_bm25`;
- **hybrid** объединение результатов dense и BM25 методом Reciprocal Rank Fusion, RRF

RRF объединяет результаты по позициям в списках, а не складывает несопоставимые исходные оценки BM25 и cosine similarity. 
В текущей конфигурации `rrf_k=60`, по умолчанию рассматриваются до 50 кандидатов каждой ветки.

Автоматический перевод русских вопросов на английский и отдельный reranker не используются.

### Векторное хранилище

Для работы сервиса построено локальное хранилище **FAISS** с двумя индексами:

- `IndexHNSWFlat` приближённый поиск по графу, `M=16`, `ef_construction=100`, `ef_search=64`
- `IndexFlatIP` точный поиск по всем сохранённым векторам, используемый как контрольный вариант

Каждый вектор связан с текстом чанка, источником, страницей и разделом. Поиск в экспериментах, CLI и RAG выполняет общий класс `Retriever`.

В `rag_answer.py` можно явно передать `--index` или `--store`. Эти аргументы взаимоисключающие. 
При `--index` загружаются артефакты из `data/indexes/`, при `--store` - готовое хранилище из `data/vector_stores/`. 
Без обоих аргументов используется последнее хранилище. Повреждённый явно указанный индекс не подменяется другой сборкой.

## Оценка поиска

### Вопросы и разметка

В `data/qrels_evidence.json` подготовлены **20 вопросов** с русскими и английскими формулировками: 
18 вопросов с ответом в документе и 2 вопроса, для которых требуется отказ. 

Для корректных вопросов заданы факты ответа и **56 evidence-цитат** (фрагментов исходного PDF, подтверждающих эти факты).

Вопросы разделены на две части:

- **DEV:** 7 вопросов, из них 6 на которые можно дать ответ, используется для выбора конфигурации
- **TEST:** 13 вопросов, из них 12 реализуемых. Используется для оценки выбранной конфигурации.

Русская и английская формулировки одного вопроса относятся к одному и тому же разбиению. 
Retrieval-метрики рассчитываются по вопросам с ответами, корректность отказов оценивается отдельно в QA.

### Метрики

Стандартные метрики вычисляются библиотекой `ir_measures`:

- **Recall@k (R@k)** доля релевантных чанков, найденных среди первых `k` результатов
- **Precision@k (P@k)** доля релевантных чанков среди первых `k` результатов
- **MRR@10** среднее обратной позиции первого релевантного результата в первой десятке, если его нет, вклад вопроса равен нулю
- **nDCG@10** качество порядка результатов с большим весом для релевантных чанков на ранних позициях

Дополнительно рассчитаны:

- **Evidence Hit@k (EH@k)** доля вопросов, для которых в первых `k` результатах нашлась хотя бы одна полная evidence-цитата
- **Fact Coverage@k (FC@k)** средняя доля фактов ответа, подтверждённых цитатами из первых `k` результатов. Для покрытия факта достаточно одного из связанных с ним evidence.

EH@k показывает, найдено ли хотя бы одно доказательство, а FC@k насколько полно поиск собрал основания для ответа. 

### Выбор конфигурации на DEV

Правило выбора зафиксировано в `source/run_experiments.py`: сначала сравнивается средний FC@5 по русским и английским вопросам в режиме dense. 
При равенстве учитываются MRR@10, затем меньшее количество чанков. Для выбранной конфигурации сравниваются dense и hybrid: 
hybrid выбирается, если его средний FC@5 выше минимум на 0,02, иначе остаётся dense.

| Конфигурация | Чанков | Средний FC@5, RU/EN dense | Средний MRR@10, RU/EN dense |
|---|---:|---:|---:|
| **markdown_header 256/32** | **832** | **0,7917** | **0,6666** |
| markdown_header 384/64 | 634 | 0,7778 | 0,5584 |
| markdown_header 480/80 | 555 | 0,6666 | 0,4537 |
| page_recursive 384/64 | 532 | 0,6528 | 0,6300 |

У выбранного варианта 256/32 средний FC@5 составил **0,7917 для dense** и **0,8750 для hybrid**. 
Поэтому итоговый выбор **256/32, hybrid**.

## Ответы языковых моделей

### Подготовка контекста и генерация

После поиска `context_builder.py` убирает одинаковые тексты, присваивает фрагментам номера `[1]`, `[2]` и далее и 
собирает контекст с указанием страниц и разделов. Фрагменты включаются целиком. Если очередной фрагмент не помещается в 
бюджет, он пропускается с записью причины.

По умолчанию для RAG запрашиваются **6 чанков**. После дедупликации и ограничения бюджета в контекст может войти меньше. 
Бюджет составляет **24 000 байт UTF-8** (это ограничение объёма текста)

Модель получает инструкцию отвечать на русском языке, использовать только переданные фрагменты и возвращать JSON с 
полями `status`, `answer`, `citation_ids`, `missing_information`. Если оснований недостаточно, ожидается `status="refusal"`.

Используются **Gemma 3 4B** и **Qwen 2.5 3B** из первой лабораторной работы через OpenAI-совместимый API Ollama. 
Имена `apollo-gemma:16k` и `apollo-qwen:16k` задают окно `num_ctx=16384`, дообучение моделей не проводилось. 
В пакетном QA использованы `temperature=0` и ограничение ответа в 500 токенов.

JSON проверяется по Pydantic-схеме. Дополнительно проверяются номера в `citation_ids` и ссылки `[n]` непосредственно в 
тексте ответа, их допустимость и согласованность между собой. Поле `citation_consistent=true` означает согласованность нумерации.

Сохранены 40 ответов, контексты, источники и параметры генерации. Ошибок разбора JSON не было.

| Показатель | Gemma | Qwen |

### Наблюдения

В Qwen Q13 в тексте ответа появилась ссылка `[9]`, хотя в `citation_ids` был только `[1]`. Это номер библиографии 
исходного PDF, перенесённый в нумерацию контекста. Старый счётчик недопустимых номеров в массиве не обнаруживал такую ошибку. 
В текущей версии проверяются и массив, и текст ответа.

В Qwen Q11 перевод описания сбора частиц солнечного ветра изменял смысл: частицы должны внедряться в алюминиевую фольгу и удерживаться в ней, 
а формулировка о прохождении через неё не передаёт этот механизм. Наличие подходящего фрагмента в контексте не устранило ошибку генерации.

В N03 источник содержит две формулировки массы образцов: 47 фунтов на странице PDF 13 и 22 кг в разделе 11.3 на странице PDF 211.
Ответ с 22 кг принят с учётом процитированного источника. 


## Выводы

Реализован полный путь от PDF до ответа с указанием источников. Для разбиения используются готовые библиотечные 
сплиттеры с учётом структуры документа, а найденный фрагмент сохраняет связь со страницей исходного PDF.

По правилу выбора на DEV лучшей стала конфигурация markdown_header 256/32, hybrid. Все три структурных варианта 
сохранили 56 из 56 evidence-цитат. Различия их retrieval-метрик показывают, что сохранение доказательства в 
корпусе и его нахождение в первых результатах - разные задачи.

На повторной TEST-оценке hybrid оказался полезнее для английских вопросов и хуже dense для русских. 
Это ограничивает вывод: выбранная конфигурация лучше по принятому DEV-критерию, но не является универсально лучшей. 
Сравнение с FlatIP также показало небольшое снижение качества HNSW в русском hybrid-поиске.

Ручная проверка отдельного QA-прогона дала 9 полностью корректных ответов из 18 у Gemma и 7 из 18 у Qwen. 
Обе модели допускали ошибки и не справились с контрольными отказами. Поэтому качество поиска, согласованность ссылок 
и фактическая правильность ответа оцениваются отдельно.
